# 官方打席視窗好球帶：已確認算法

查核日期：2026-10-24。指定頁：https://stats.cpbl.com.tw/schedule/2026-C-4 。本次 HTTPS 連線恢復，已直接取得頁面、公開前端程式、球員資料與單場 JSON；補足先前研究尚未確認的部分。

## 1. 身高資料與白框

打席視窗依事件的 `hitterAcnt` 查詢 `/v1/players/{id}`。原始回應路徑為 `Data.Player.Basic.Height`；前端轉成 `data.player.basic.height`，除以 100 成為公尺。

前端共用數學模組 459909 的規則：

```text
bottom = 0.27 × heightM
top    = 0.535 × heightM
left   = -0.2158
right  = +0.2158
```

因此框寬 0.4316 公尺，框高度依名冊身高改變。缺少有效正身高時，轉換函式回傳 undefined，框函式使用預設身高 1.803 公尺。

這是官方網站的身高比例顯示算法；沒有在此流程看到逐球從影像量測肩、腰、膝或打擊姿勢。白框不是依該打席球點擬合出來；同一打者身高資料不變時，框尺寸相同。

## 3. 圖上的位置不是直接原始球點

原始資料提供 `PlateLocSide`、`PlateLocHeight`，但打席 SVG 先呼叫共用軌跡函式，取得本壘板中間平面的點，再繪圖。

對軌跡各軸使用 `P(t)=c0+c1*t+c2*t²`。前端求出兩個球往前飛、時間為正的交點：

- 前緣平面：軌跡 X=0.4318。
- 中間平面：軌跡 X=0.2159。

前端場景座標對應：橫向=-軌跡 Z，高度=軌跡 Y，場景深度=軌跡 X+0.7682。中間平面的場景深度為 0.9841，白框亦放在這個深度。

在前緣交點，程式先把軌跡平移，使橫向、高度與官方 Location 的球點一致，再取中間平面的座標。等價公式：

```text
x_display = PlateLocSide - Z(t_middle) + Z(t_front)
z_display = PlateLocHeight + Y(t_middle) - Y(t_front)
```

這是以官方球點錨定軌跡、往板面中央推進的顯示換算。不是單純直接把 ZoneTime 代入公式，也不能說這個推算點比官方測量點更準。

如果沒有有效 Location、ZoneTime、完整三軸係數或求不到前向交點，這個函式回傳 null，2D 圖不畫該點。這也是畫面球點數可能少於投球數的原因之一。

例如第 3 球原始高度 0.663135072 公尺，換算顯示高度約 0.627663021 公尺，相差約 3.55 公分；若直接畫原始高度，球會比官網畫得高。

## 4. SVG 像素換算

本打席圖使用 SVG viewBox 384 × 512，座標範圍：橫向 -0.55～0.55、高度 0.15～1.55。

```text
pixelX = (-x_display + 0.55) / 1.10 × 384
pixelY = (1.55 - z_display) / 1.40 × 512
```

橫向有反號；高度越高，SVG 的 y 越小。白框以相同換算畫出，九宮格線切成三等份。

曾頌恩白框在 SVG 中約為左 116.67、右 267.33、上 218.59、下 391.09。圖隨容器尺寸等比例縮放，所以截圖中實際像素不一定是這些數字。

第 1 球的換算高度約 -0.0445，對應 SVG y 約 583，超過 512，因此不在可見畫布內；原始資料中仍然存在。第 8 球 SVG y 約 66，對應截圖上方的綠色 8。

圓點大小由框寬推導（半徑=繪圖框寬/12），搭配編號與描邊；不要直接把畫面邊框或抗鋸齒像素當作精確球體接觸測量。

## 5. 兩張圖的顏色與白框意義

- 本打席紀錄圖：以事件 `isBall/isStrike` 著色。壞球綠，好球事件紅，包含判好球、揮空、界外等。沒有依球點是否在框內重新上色。
- 全場投打對決圖：依人工球種 `TaggedPitchType` 分組，快速球紅、變化球藍，不是好壞球或誤判。
- 2D 與 3D 元件均使用共用身高框函式；3D 白框亦在中間平面。

截圖第 5、6、7 球即使在框外仍是紅色，因為分別是揮空、界外、界外；不能把紅色框外球都算成主審誤判。
