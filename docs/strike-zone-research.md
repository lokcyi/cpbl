## 三個專案的差異

### CPBL umpire scorecard

先前讀取的 `report_2026-C-1.html` 中，繪圖使用 `SZ_BOTTOM=0.486`、`SZ_TOP=0.963`，每球另有 `sz_bottom`、`sz_top`，並以：

```text
z_display = SZ_BOTTOM + (z - sz_bottom) * (SZ_TOP - SZ_BOTTOM) / (sz_top - sz_bottom)
```

正規化球點高度。這證明共同繪圖框與每球個人框是兩件事，不能將固定展示框視為所有打者的真實好球帶。

作者先前公開說明稱，官網好球帶依球員身高動態調整。但公開倉庫主要是產生後的報告，尚未取得產生 `sz_bottom`、`sz_top` 的程式與經驗證比例。不能從固定展示常數反推並宣稱已找出個人框算法。

紅色主審估計區域亦須與規範框區分：擬合主審好球判決機率得到的區域是在描述判決習慣，不是建立球員的客觀合法好球帶。

來源：[報告原始碼](https://github.com/yuetsu001/cpbl-umpire-scorecard/blob/main/reports/report_2026-C-1.html)、[作者說明](https://www.ptt.cc/bbs/Baseball/M.1785336874.A.314.html)。以上為先前閱讀結果，本次未能更新遠端版本。

### cpbl-savant-py-app

先前查核的 `analysis/trackman.py` 從官方 `LiveLog` 擷取 `PlateLocSide` 與 `PlateLocHeight`。熱圖使用固定近似框（橫向半寬 0.215、下緣 0.46、上緣 1.07），不是每位打者的個人框。可參考資料解析方式，但不能直接沿用該框建立裁判精確評分。

來源：[逐球分析程式](https://github.com/lin-junyou/cpbl-savant-py-app/blob/master/analysis/trackman.py)。

### abs-tracker

先前查核的 `update.py` 使用 MLB 資料中的 ABS 挑戰事件及 `is_overturned`，不是自行從球點與身高重判。移植其統計不會自動解決 CPBL 個人好球帶問題。

來源：[資料處理程式](https://github.com/jasonbhorne/abs-tracker/blob/main/update.py)。

## 本次座標實驗：801 筆

程式：`node scripts/audit-coordinates.mjs`。

資料：`research/cpbl_raw/2026-A-211.json`、`2026-D-166.json`、`2026-C-1.json`。只取同時有完整軌跡係數、ZoneTime 與球點的紀錄；不是完整球季抽樣。

對三個係數採用假設：

```text
P(t) = c0 + c1*t + c2*t²
t = Trackman.Pitch.Location.ZoneTime
```

得到：

| 場次 | 可驗算筆數 | X(t) 中位數 | 高度差最大絕對值 | 橫向反號差最大絕對值 |
|---|---:|---:|---:|---:|
| 2026-A-211 | 326 | 0.433506 | 0.0049995 | 0.0038444 |
| 2026-D-166 | 257 | 0.433421 | 0.0069905 | 0.0035433 |
| 2026-C-1 | 218 | 0.433395 | 0.0050560 | 0.0038628 |

高度差定義為 `Y(t) - PlateLocHeight`；橫向差定義為 `Z(t) + PlateLocSide`。單位沿用原始資料；若座標單位確認為公尺，高度差最大約 7 mm、橫向差最大約 3.9 mm。但不能將這些數值稱為儀器測量誤差或實際準確度。

另取速度導數 `sqrt(X'(t)^2+Y'(t)^2+Z'(t)^2)*3.6` 與 `ZoneSpeed` 比較，三場 RMSE 約 0.20–0.24。這與位置公尺、時間秒、球速 km/h 的假設相容，但仍需要官方資料字典確認單位及座標原點。

重要結論：

- 此係數解讀下，軌跡 Y 對應高度，軌跡 Z 與公開橫向位置反號；不能把軌跡 X/Z 直接當成繪圖的橫向／高度。
- ZoneTime 的縱向位置集中約 0.433；不是把縱向 X 設 0 就能直接取得相同球點。0.433 接近 17 英吋的公尺值，但「因此必然是本壘板前緣」目前只是待確認假設。
- 官方球點欄位與多項式在毫米量級上並非完全一致；不可自行宣稱多項式重算值更準，或擅自把差值當成應修正的偏差。
- 同源資料吻合是內部一致性，不是與獨立實測真值的校準。

詳細輸出：[coordinate-audit.json](../research/strike-zone/coordinate-audit.json)。

## 正確建立個人框的優先順序

1. **官方逐球／逐打席上下界**：若取得官方當時使用的個人框，直接保存原值、單位、適用日期與規則版本。
2. **已驗證的官方身高換算方式**：只有取得官方顯示算法後，才以球員 ID 串接當期身高，算出框。明確標示身高模型與估計性質；名冊身高不是揮棒準備姿勢的實際量測。
3. **人工標記或影片姿勢量測**：需有攝影機校正、地面／本壘板參考與符合規則的姿勢定義，不能直接把轉播像素當成公尺。此方法需另作精度驗證。

不以主審既有判決擬合的邊界充當個人規範框；若研究判決習慣，將其另列為估計判決區域。

個人框資料表至少保存：球員 ID、身高來源及日期、上下界、寬度、適用平面、單位、方法、規則版本、估計或官方標記，以及可取得的不確定性。使用估計身高框時不宣稱正式 ABS 結果。

## 判定球體與框的交集

先確認採用的是哪種規則：單一平面 ABS 判定、三維合法好球帶，或網站自己定義的近似平面框。不能混稱。

若採用「球體在該平面的投影圓與矩形框是否相交」，令橫向半寬為 `w/2`、上下界為 `bottom/top`、球半徑為 `r`，球心為 `(x,z)`：

```text
dx = max(abs(x) - w/2, 0)
dz = max(bottom - z, z - top, 0)
distance_to_rectangle = sqrt(dx² + dz²)
overlap = distance_to_rectangle <= r
```

這比只判球心是否在框內完整；也比直接把框的四邊各外擴一個球半徑更正確地處理四角。這是條件幾何公式，並非已確認的 CPBL ABS 實作。實際應使用哪個球半徑、平面與接觸規則仍待官方依據。

若規則考慮整個本壘板上方的三維空間，需使用整段軌跡及板面幾何，不能用單個前緣球點完全替代。

## 如何評估座標是否足夠可靠

分開檢查：

1. 取得／解析：保留原始 JSON、事件 ID、官方球點與軌跡，缺值不能轉成 0。
2. 座標約定：確認單位、方向、原點、球心與取樣平面。
3. 事件對應：確保球點對應同一球、同一投打者，排除換人及非投球裁定。
4. 內部一致性：像本次多項式驗算，記錄偏差及離群點。
5. 真實精度：需要儀器校正、官方驗證、獨立量測或可信參考資料；現有 JSON 單獨無法提供。

捕手接球點、電視九宮格、官網雷達球點不能未經校正直接互相當作真值。樣本中的 `Hit.LandingFlat.Confidence` 屬於擊球落點，不應誤用為投球進壘點的信心值。

## 對目前網站的建議

維持原始球點展示；新增欄位時先保存「官方框」與「估計框」的來源。下一個應驗證的項目是：官方打者個人頁／前端繪圖程式的高度來源、比率或姿勢設定，以及投球座標字典。未完成以前不開啟裁判準確率排名。

未來若做相符率：官方框與估計框分開計算；對框高度、球半徑、容錯設定做敏感度分析，將邊界附近歸入不確定區，展示涵蓋率與排除數，不用一個沒有依據的固定容錯就宣稱精確。
